# Домейн модел `EvidenceRelation` — дизайн скица

**Статус:** ДИЗАЙН (не имплементиран).  Отговаря на тавана, потвърден през одити
v16–v19: класификаторът по име/клас не може да реши *грешна система*, *производни
количества*, *сегментирано покритие*, *композитни* и *multi-column* BOQ редове.

**Централен принцип (непроменен):** детерминистичният код има последната дума.
AI-ът **предлага** структурни връзки; сървърът ги **проверява** и брои само
доказаните.  При невъзможност за проверка → не се брои → редът е непокрит →
блокиран (fail-closed).  Никаква връзка не се вярва на AI-а „на доверие".

---

## 1. Защо класификаторът има таван

`analyze_boq_coverage` днес пита: „има ли производствена дейност от правилния
**клас**, която цитира този ред и количеството съвпада?".  Това не различава:

| Таван | Пример | Защо класът не стига |
|---|---|---|
| Грешна система | Водопровод ул.А (100 m) „покрит" от Полагане **канализация** ул.Б (100 m) | и двете са клас `laying` |
| Производни к-ва | Тръба 100 m; Изкоп **144 m³** | различна мярка → днес е mismatch, а е геометрично производно |
| Сегментирано | BOQ 100 m; Участък-1 60 m + Участък-2 40 m | всяко поотделно е mismatch |
| Композитно | „Изкоп **и** полагане 100 m" (един ред) | класифицира се като ЕДИН клас; липсващото полагане не се лови |
| Multi-column | Един Excel ред: Дължина 100 m **и** Брой 5 бр | става един `QuantityRow`; второто количество е невидимо |

Общото: покритието не е „клас съвпада", а **„физическата работа отговаря на
обещаното количество, за същия актив, в същата система, на същото трасе"**.

## 2. Entities

```python
@dataclass(frozen=True)
class BOQItem:
    ref: str                 # document!sheet!row!column  ← вкл. КОЛОНАТА (multi-column)
    description: str
    quantity: float
    unit: str                # нормализиран
    system: str              # water | sewer | road | electrical | telecom | other  (server-derived)
    alignment: str | None    # трасе/улица/участък, ако е извлечим (server-derived)
    required_classes: tuple[str, ...]   # ≥1; композитен ред → напр. (excavation, laying)

@dataclass(frozen=True)
class Activity:              # задача от графика (server-нормализирана)
    id: str
    activity_class: str      # вече server-derived (одит v16)
    system: str              # server-derived от име/описание
    alignment: str | None    # server-derived, свери с whitelist от ситуацията
    quantity: float | None
    unit: str
    claims_ref: str          # кой BOQItem твърди, че обслужва (source_ref)

class RelationType(Enum):
    COVERS = "covers"                       # пряко изпълнява обещанието
    CONTRIBUTES_TO = "contributes_to"       # сегмент/частично (сумира се)
    DERIVES_FROM_GEOMETRY = "derives_from"  # количеството е геометрично производно

@dataclass(frozen=True)
class EvidenceRelation:      # РЕБРО Activity → BOQItem, СЛЕД сървърна проверка
    activity_id: str
    boq_ref: str
    kind: RelationType
    verified: bool           # сървърът потвърди ли класа/системата/трасето/геометрията
    reason: str              # защо (за одит следа); при not verified — какво липсва
```

`PhysicalAsset` (тръбен участък, шахта, пътен сегмент) остава **имплицитен** в
първите фази — идентичността му е (`system`, `alignment`, `DN`).  Въвежда се
експлицитно само ако сегментирането го наложи.

---

## 3. Правилото за покритие (server-owned)

За всеки `BOQItem` и всеки клас в `required_classes`:

```
matches = активности A, за които СЪРВЪРЪТ е потвърдил:
            A.activity_class == изисквания клас
        И  A.system        == BOQItem.system
        И  A.alignment     съвпада с BOQItem.alignment (или whitelisted)
        И  релацията е COVERS или CONTRIBUTES_TO

allocated = Σ A.quantity по matches       (сегментиране: 60 + 40 = 100)

ако |allocated − BOQItem.quantity| / BOQItem.quantity ≤ TOL:  клас-ът е ПОКРИТ
ако > 1 пълен COVERS на същия клас:                          over_covered
ако allocated == 0:                                          класът е НЕПОКРИТ
```

`BOQItem` е **покрит** само когато ВСИЧКИ `required_classes` са покрити (композит).
`DERIVES_FROM_GEOMETRY` активности се **отчитат като легитимни** (не са mismatch),
но **не броят** към покритието — тръбният ред пак иска `laying` покривач.

---

## 4. Как всеки таван пада

**Грешна система.**  `system` е server-derived (лист „Канализация" → sewer;
описание „водопровод" → water).  COVERS изисква `A.system == BOQItem.system` →
полагане-канализация не покрива водопроводен ред, дори класът да е `laying`.

**Производни количества.**  Нова детерминистична таблица `geometry.json`
(сечение на изкоп по DN/дълбочина, аналог на `productivities.json`):
```
изкоп_обем ≈ дължина × ширина_на_траншея(DN) × дълбочина
```
Сървърът приема `DERIVES_FROM_GEOMETRY`, ако Изкоп 144 m³ ≈ 100 m × сечение(DN400).
→ вече не е mismatch, но и не покрива; редът пак иска полагане.

**Сегментирано.**  `CONTRIBUTES_TO` allocations се СУМИРАТ по (ref, клас):
60 + 40 = 100 → покрит.  Всяко поотделно вече не е mismatch.

**Композитно.**  При индексиране „Изкоп **и** полагане" дава
`required_classes = (excavation, laying)`.  Липсва ли полагане → редът е непокрит.

**Multi-column.**  `build_quantity_index` емитира **по един `BOQItem` за всяка
количествена колона** (Дължина, Брой), с колоната в `ref`
(`document!sheet!row!column`).  Двете количества стават независимо проверими.

## 5. Trust boundary (къде AI-ът НЕ се вярва)

| Поле | Източник | AI ролята |
|---|---|---|
| `activity_class` | сървър, от името (v16) | игнорира се, трие се |
| `system` | сървър, от лист/описание | подсказка, пре-извежда се |
| `alignment` | сървър, свери с whitelist от ситуационния план | подсказка, пре-извежда се |
| `required_classes` | сървър, от BOQ описанието | — |
| геометрия (производни) | `geometry.json` (детерминистично) | — |
| `RelationType` | AI **предлага**, сървър **проверява** | предложение, не доказателство |

Непроверима връзка → `verified=False` → не се брои.  Точно както днес неразпознат
клас не покрива — само че сега проверката е по-богата.

## 6. Фазова миграция (всяка фаза е самостоятелна и fail-closed)

Всяка фаза съжителства с текущия `analyze_boq_coverage` и НЕ отслабва защитата —
непроверено винаги пада към „непокрит → блокиран".

1. **Фаза 1 — `system` + multi-column.**  Добави `system` към `BOQItem`/`Activity`
   (от лист/описание) и емитирай по един BOQItem на количествена колона.
   *Пада: multi-column.  Отключва: проверка по система.*
   Малък, изолиран; тества се с fixture като `test_boq_coverage_fixture.py`.
2. **Фаза 2 — `alignment` match в COVERS.**  Свери трасето с whitelist от
   ситуацията (вече имаме `extract_situation_locations`).  *Пада: грешна система/трасе.*
3. **Фаза 3 — `geometry.json` + `DERIVES_FROM_GEOMETRY`.**  *Пада: производни к-ва.*
   Иска нова верифицирана таблица (сечения) — единствената съществена нова
   доменна информация.
4. **Фаза 4 — `CONTRIBUTES_TO` сумиране.**  *Пада: сегментирано покритие.*
5. **Фаза 5 — композитни `required_classes`.**  *Пада: композитни редове.*

Редът е по съотношение стойност/риск: Фаза 1–2 махат двата най-опасни
false-positive-а (грешна система, невидима колона) с малко код и без нова доменна
таблица.  Фаза 3 е най-тежката (иска геометрия).

---

## 7. Какво реално е нужно като нова информация (честно)

- **`system`, `alignment`** — извеждат се детерминистично от лист/описание/ситуация;
  без нов ръчен вход.  Fail-closed при неяснота.
- **`geometry.json`** — ЕДИНСТВЕНАТА съществена нова верифицирана таблица (сечения
  на траншея по DN/дълбочина).  Полева проверка, като `productivities.json`.
- **AI изход** — от „познай покритието" към „декларирай (дейност → BOQ ref,
  тип-връзка)".  Сървърът пресмята истината; декларацията е само подсказка.
