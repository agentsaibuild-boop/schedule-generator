## 3. Детекционни фикси — доказани от реален КСС

Реалните КСС ползват нотация, която старият код не разпознаваше. Всеки фикс е
код (не измислени числа) и е обвързан с тест:

| # | Проблем (реални данни) | Фикс | Файл |
|---|------------------------|------|------|
| 1 | „Ф300" не се четеше като DN (само „DN300") | `_DN_RE` приема Ф/Φ/Ø/⌀ | `duration_calculator.py` |
| 2 | Няма шаблон за **PP** (полипропилен) | нов PP шаблон + хомоглиф РP→PP | `duration_calculator.py` |
| 3 | Материалът в клетка „diameter" не се четеше | haystack включва diameter/описание | `duration_calculator.py` |
| 4 | Мерна единица „**брой**" не се разпознаваше | добавена към count единиците | `duration_calculator.py` |
| 5 | **Промптът не позволяваше PP** → моделът пишеше PE | `SUPPORTED_MATERIALS` enum + PP | `ai_processor.py` |

Точка 5 е коренът на PE/PP объркването, наблюдавано при реалния тест: промптът
разрешаваше само `PE, CI, PVC, AC, GRP`. Сега enum-ът се извежда от единен
източник (`SUPPORTED_MATERIALS` в `duration_calculator.py`), който ползват и
промптът, и JSON schema-та — не могат да се разминат.

## 4. Fail-closed поведение — гейтът е доказан на живо

Реалният тест (DeepSeek worker, defective изход) **потвърди**, че
детерминистичният гейт отхвърля невалиден график, дори когато AI-ят го е
маркирал „approved":

- DeepSeek генерира счупени графи (фантомни ID: „задача 2 зависи от несъществуващо
  ID 1") → **гейтът ги ОТХВЪРЛИ всеки път**.
- Продължителности без доказана норма → маркирани `NOT_PROVEN` (не се експортират).

**Одиторска проверка:** `tests/test_validation_gate.py`,
`tests/test_export_policy.py` — невалиден/недоказан график НЕ става
одобрен+експортируем под нито една политика.

## 6. Structured output + streaming (PR #2)

- **`build_schedule_response_schema()`** (`ai_processor.py`) — JSON schema с
  `material` като enum (= `SUPPORTED_MATERIALS` + празно/null). Подава се на
  worker-а. **Best-effort:** при отказ на модела/SDK повтаря заявката БЕЗ schema
  → генерацията никога не се чупи.
- **Streaming** (`_chat_worker_claude`) при `max_tokens ≥ 8000` — маха HTTP
  timeout риска при дълъг генериращ отговор.
- **Разделение:** schema пази ФОРМАТА и валидните материали; референтната цялост
  на графа (фантомни ID) остава на детерминистичния гейт.

**Тестове:** `tests/test_ai_router.py` (mock streaming/fallback),
`tests/test_ai_processor_pure.py` (enum синхрон с детектора).

## 8. Известни ограничения (честно)

1. **Не е тестван реален Sonnet run** — изисква Anthropic кредити (изчерпани по
   време на сесията). Structured-output API пътищата (`output_config` за Claude,
   `response_format` за DeepSeek) са best-effort с fallback, но НЕ са валидирани
   срещу жив модел. Ще се докажат при следващия Sonnet тест.
2. **Норми от полево правило**, не лабораторно (раздел 2). Настилки/бордюри —
   избрани от диапазон за конкретния обект.
3. **Остатъчни NOT_PROVEN** (коректно, по решение): водомерна/преливна шахта,
   бетонов кожух, УО оттоци — нямат норма, гейтът ги маркира.
4. **DeepSeek е слаб** за този домейн (счупени графи, под-генериране). Препоръка
   от проучването: worker = Claude Sonnet 5, controller = Opus 4.8/5; по-евтина
   алтернатива за A/B = Gemini 3 Pro.
