**Комити от одита насам:** `c2218f2`, `44d9370`
**Тестове:** 1519 (unit, `--ignore=tests/e2e`)

Този документ разделя **проверени свойства** от **намерения** и от **известни
ограничения**. Предишни версии на описанието представяха второто като първо;
одитът основателно го наби, затова тук границата е изрична.

Ключова уговорка, важи за целия документ: **нищо не е проверено срещу реален
тръжен проект, нито на машина с MS Project.** 1519 теста доказват, че кодът
прави каквото твърди — не че моделът генерира верни графици от истински
документи.

## 2. Веригата на генериране

```
документи (папка на диск)
  ↓ file_manager — класификация ПО СЪДЪРЖАНИЕ, не само по име
  ↓   text/thin/scanned по страница; КСС се разпознава по таблица вътре
  ↓ prompt_safety — ограда с nonce; текстът е ДАННИ, не инструкции
анализ (AI) — извлича количества, пикетаж, топоними
  ↓ provenance — индексира количествените редове с точен ref
  ↓ knowledge_manager — подбор на уроци по релевантност
генериране (AI) → параметри + source_ref (цитат към ред от КСС)
  ↓ duration_calculator — норми от productivities.json
  ↓ recompute_durations — детерминистични продължителности + произход
  ↓ verify_citations — цитатите се проверяват срещу документа
верификация (AI контрольор)
  ↓ restore_determinism — числата се връщат след AI correction
обогатяване (AI) — САМО описателни полета (wbs, notes); планиращите — карантина
  ↓ ★ schedule_builder.validate_schedule — ДЕТЕРМИНИСТИЧЕН GATE
  ↓   зависимости, дати, цикли, FS/SS/FF/SF, пространствени сблъсъци
експорт: XML / PDF / Gantt — само ако графикът е EXPORTABLE
```

Последната **разрешаваща** дума е код, не AI. Това е централната поправка от
одита.

## 3. Проверени свойства (код + тест)

### 3.1 Невалиден график не става официален резултат
Централната находка на одита е затворена.
- `validate_schedule` се вика след последната AI стъпка (`ai_processor.py`).
- При `valid=False`: статусът става `invalid`, графикът НЕ става
  `current_schedule`, не се записва в проекта, а export бутоните са
  `disabled` (`app.py`).
- AI статусът се пази отделно като `ai_status` — не се крие, но не решава.
- Тестове: `test_validation_gate.py` (25), вкл. точния сценарий
  „AI approved + validation invalid → invalid".

### 3.2 AI не пренарежда графика след изчислението
- `apply_corrections` връща цял график; след него `restore_determinism`
  преизчислява продължителностите наново и докладва премахнати/добавени
  задачи.
- `enrich_for_msproject` прилага само `wbs`, `notes_msp`; планиращите полета
  (`dependency_type`, `lag_days`, `is_milestone`, `constraint_type`) отиват в
  карантина `msp_suggestions`, не в графика.
- Тестове: `test_enrichment_quarantine.py` (21).

### 3.3 Ръчната модификация минава през същия gate
- `_handle_modify_schedule`: преизчисляване → пълна валидация → gate.
- Команда „намали срока с 20 дни", която връща duration=-5 / кръгова
  зависимост, се ОТХВЪРЛЯ — предишният график остава.
- Тестове: `test_modification_gate.py` (14).

### 3.4 Продължителностите имат деклариран произход
- Всяка задача носи `duration_source` = `calculated` | `suggested` + машинен
  код на причината (`MISSING_MATERIAL`, `NO_PRODUCTIVITY_RULE`...).
- Изчисленото живее отделно в `calculated_duration`.
- Тестове: `test_duration_provenance.py`, `test_duration_calculator.py`.

### 3.5 Количествата имат произход — документ / AI / човек
- `provenance.py`: индексира КСС редовете с `документ!лист!ред`.
- Моделът цитира `source_ref`; `verify_citations` дава 4 изхода:
  `verified` / `mismatch` / `unknown_ref` / `uncited`.
- **`mismatch` (число ≠ цитирания ред) е най-опасният** — показва се пръв.
- Ръчна промяна → `human_override`, заменя документа, не се сверява.
- Тестове: `test_provenance.py` (59).

### 3.6 Пространствена валидация (пикетаж)
- `spatial.py`: сблъсък на бригади (един метър, един ден), дължина на открит
  изкоп (сума по място за ден).
- Добавъчен: задачи без пикетаж не участват, съществуващите графици не се
  чупят. Покритието се съобщава ВИНАГИ.
- Жив тест: 14/17 задачи с пикетаж, хванат реален сблъсък ЕВ2×ЕВ2.
- Тестове: `test_spatial.py` (30).

### 3.7 Валидаторът е пълен и устойчив
- FS/SS/FF/SF с лаг (беше „всичко е FS"): `test_dependency_semantics.py` (28).
- Отрицателна продължителност → грешка; низ в поле → грешка, не срив.
- dict зависимости не сриват (беше `TypeError`).
- Празно ID → грешка; застъпване на екип при 2 задачи (беше 3).

### 3.8 Провалът не се маскира като резултат
- `json_contract.py`: нечетим AI отговор → грешка, не „графикът има проблеми".
- Отрязан отговор (`finish_reason=length` / `stop_reason=max_tokens`) спира
  генерирането с ясна причина, не минава за „невалиден JSON".
- Тестове: `test_json_contract.py` (29), `test_truncation_handling.py` (14).

### 3.9 MS Project XML — two-pass + round-trip
- Two-pass: зависимостите не изчезват според реда на задачите (беше тихо).
- **SS/SF в type map бяха РАЗМЕНЕНИ** — открито с round-trip, поправено.
  Съществуващият тест потвърждаваше дефекта.
- Milestone `PT0H0M0S`; `Must Start On` избираем; календарна аритметика
  (работни дни, не календарни).
- `import_xml.py` чете обратно; `compare_schedules` сверява.
- Тестове: `test_xml_roundtrip.py` (25), `test_xml_two_pass.py`,
  `test_xml_msproject_semantics.py`.

### 3.10 Сигурност
- **Self-evolution ИЗКЛЮЧЕН по подразбиране** (`ENABLE_SELF_EVOLUTION`), на
  всяко ниво: вход, analyze, generate, apply, backup, confirm.
- Поправена пробойна: `.env` се четеше през AI план (`resolve_safe_path`
  вече пази и четенето, не само записа).
- `ADMIN_CODE` маскиран преди диска; `secrets.compare_digest`.
- Тестове: `test_self_evolution_guards.py` (70).

### 3.11 Прозрачност — EU AI Act чл. 50
- Маркиране в чат (50.1), PDF, XML, JSON данни (50.2).
- Тестове: `test_ai_disclosure.py`.

### 3.12 Вход и разбиране на документите (BACKLOG)
- КСС по СЪДЪРЖАНИЕ (`find_boq_by_content`) — файл с друго име, но с таблица
  вътре, вече минава: `test_boq_by_content.py` (19).
- Контекст: 400k бюджет (беше 120k = 21% от модела), приоритет по роля,
  видим отчет какво е отрязано: `test_context_budget.py` (22).

## 4. Известни ограничения (НЕ проверени / НЕ направени)

| # | ограничение | състояние |
|---|---|---|
| 4.1 | **Нищо не е тествано на реален проект** | доказано срещу тестове/синтетика |

експорт и моят четец се разбират — НЕ че MS Project ги разбира по същия
начин. `ConstraintType=2`, календарът, `Text4` при Save As `.mpp` — всичко
това чака проверка на машина с Project.

## 6. Какво да прегледа одиторът първо

По ред на риск:

1. `src/schedule_builder.py :: validate_schedule` — gate-ът и пълнотата му
2. `src/ai_processor.py :: generate_schedule` — редът на стъпките, къде е gate-ът
3. `src/ai_processor.py :: _restore_determinism_after_ai` — AI correction
4. `src/chat_handler.py :: _handle_modify_schedule` — modification път
5. `src/provenance.py :: verify_citations` — mismatch логиката
6. `src/spatial.py` — пространствените проверки
7. `src/export_xml.py :: _DEPENDENCY_TYPE_MAP` + `import_xml.py` — round-trip
8. `src/self_evolution.py :: is_enabled` + guard точките
9. Тестовете, които твърдят, че пазят горното — дали проверяват поведение,
   не наличие на текст (одитът с право посочи `inspect.getsource` тестове)
